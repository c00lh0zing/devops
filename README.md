## Назначение

Pipeline позволяет снимать и возвращать нагрузку на бекенд-ноды на всех балансировщиках одновременно. Основной сценарий использования — rolling update бекенд-серверов без простоя.

## Параметры pipeline

### ACTION

Выбор действия:

- **drain** — снять нагрузку со всех бекенд-нод на всех балансировщиках, кроме выбранной в `KEEP_BACKEND`. Трафик будет идти только на одну ноду.
- **swap** — снять нагрузку с выбранной в `KEEP_BACKEND` ноды и вернуть нагрузку на все остальные. Трафик пойдёт на все ноды, кроме выбранной.
- **restore** — вернуть нагрузку на все ноды бекенда. Штатный режим работы. Параметр `KEEP_BACKEND` игнорируется.

### KEEP_BACKEND

IP-адрес бекенд-ноды, относительно которой выполняется действие:

- При `drain` — эта нода остаётся активной, остальные выводятся.
- При `swap` — эта нода выводится, остальные возвращаются в работу.
- При `restore` — игнорируется.

### DRY_RUN

Режим проверки без применения изменений (по умолчанию выключен).

Если включён:
- Конфиг скачивается с каждого балансировщика и модифицируется локально.
- В логе отображается состояние upstream **до** и **после** модификации.
- Изменённый конфиг **не загружается** на балансировщик, бекап **не создаётся**, рестарт **не выполняется**.

Позволяет увидеть какие именно изменения будут внесены, прежде чем применять их на продакшене.

## Алгоритм работы

Pipeline последовательно обрабатывает каждый балансировщик. Для каждого из них выполняются следующие шаги:

```
1. scp: скачать текущий конфиг syngx.conf с балансировщика
2. grep: вывести текущее состояние upstream-секций (для контроля в логе)
3. sed: модифицировать конфиг локально:
   a. Нормализация — убрать все маркеры 'down' с бекенд-серверов
   b. Добавить 'down' нужным нодам в зависимости от ACTION
4. grep: вывести состояние upstream после изменений (для контроля в логе)

   --- если DRY_RUN включён, обработка балансировщика на этом завершается ---

5. cp: создать бекап syngx.conf.bak на балансировщике
6. scp: загрузить изменённый конфиг обратно на балансировщик
7. syngx -t: проверить валидность конфига
8. Если проверка OK  → systemctl restart syngx
   Если проверка FAIL → восстановить бекап, остановить pipeline
```

### Модификация конфига (sed)
<details>
 <summary>Spoiler</summary>



Pipeline работает с текущим конфигом, скачанным с ноды, а не с заранее подготовленными файлами.

Модификация выполняется в два этапа:

1. **Нормализация** — из всех строк `server <backend_ip>:<port> ... down;` удаляется маркер `down`. Это защищает от дублирования `down` при повторных запусках.
2. **Применение действия** — маркер `down` добавляется к нужным бекенд-нодам согласно выбранному `ACTION`.

Пример трансформации при `drain` с `KEEP_BACKEND=10.119.121.44`:

```nginx
# До (исходный конфиг)
upstream backend {
    server 10.119.121.44:443;
    server 10.109.37.176:443;
}

# После
upstream backend {
    server 10.119.121.44:443;
    server 10.109.37.176:443 down;
}
```

Закомментированные строки (начинающиеся с `#`) не затрагиваются.
</details>

## Типовой сценарий: rolling update бекендов

### Шаг 1 — вывод основной группы бекендов

Запустить pipeline:
- `ACTION` = **drain**
- `KEEP_BACKEND` = **10.119.121.44**

Результат: трафик идёт **только** на `10.119.121.44`. Остальные ноды (`10.109.37.176`, `30.88.36.249`, `30.88.81.1`) помечены как `down` на всех балансировщиках.

Выполнить обновление/обслуживание на выведенных нодах.

### Шаг 2 — переключение нагрузки

Запустить pipeline:
- `ACTION` = **swap**
- `KEEP_BACKEND` = **10.119.121.44**

Результат: нода `10.119.121.44` помечена как `down`, все остальные ноды **возвращены** в работу.

Выполнить обновление/обслуживание на `10.119.121.44`.

### Шаг 3 — возврат в штатный режим

Запустить pipeline:
- `ACTION` = **restore**

Результат: все бекенд-ноды активны на всех балансировщиках. Штатный режим работы.
